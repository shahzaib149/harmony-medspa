# Analytics maintenance

The marketing app owns browser tracking. Do not add tracking to the CRM as part of this setup.

- `app/layout.tsx` renders `components/GoogleAnalytics.tsx` once in `<head>`. Its native inline bootstrap initializes the queue while parsing HTML, then creates one async Google loader. In installed Next 16, `beforeInteractive` inline scripts queue behind the Next runtime; React 19 also hoists JSX async scripts. Creating the async loader after the stub avoids both timing/order problems. Public helpers live in `lib/analytics.ts`; its self-contained runtime is serialized; production browser tests must verify it after minification.
- **Manual page views only:** the bootstrap records the initial view; `AnalyticsNavigation` records committed pathname/search changes and back/forward visits. They share URL deduplication; a head observer waits through transient empty titles during navigation. Hash-only changes do not count. Both config commands use `send_page_view:false`. **Before release, disable GA4 Enhanced measurement → Page views → Page changes based on browser history events.** That account setting is separate from `send_page_view:false`; leaving it on produces duplicates. See [Google's guidance](https://developers.google.com/analytics/devguides/collection/ga4/views).
- Metadata is not streamed (`htmlLimitedBots: /.*/`) so the committed page title is available before a page view. This trades dynamic-page TTFB for reliable titles. Root default supplies the home title and root `title.template` supplies the sole brand suffix. New pages export their own title segment; CMS blog suffixes are normalized. Never synthesize a different analytics title.
- Click IDs (`gclid`, `gbraid`, `wbraid`), all `utm_*`, and existing device/network/matchtype fields are captured on initial load and navigation into first-party `localStorage` key `harmony_attribution_v1`. Expiry is 90 days, enforced when read. A new paid click replaces the campaign; browsing and organic links cannot overwrite or extend a paid click. Blocked storage falls back to document memory (cannot survive a full reload). Forms read storage, not the submission URL.
- New forms must call `submitLead` or `submitLeadPayload`, await its branded successful response, then call `trackLead(response)` in their success handler. HTTP failures and rejected fetches throw before this token is issued. Reusing a successful response cannot emit a second pair. A 2xx response means Make acknowledged the webhook; confirming the Airtable write still requires an end-to-end test. Never send names, email, phone, message text, or treatment details to GA/Ads.
- Set `NEXT_PUBLIC_GA4_MEASUREMENT_ID`, `NEXT_PUBLIC_GOOGLE_ADS_CONVERSION_ID`, and `NEXT_PUBLIC_GOOGLE_ADS_LEAD_SEND_TO` in Vercel **Production** before building. These values are compiled into the public bundle. Production builds fail for absent/malformed IDs. GA4 currently observed: `G-HRPTWTFKNB`; Ads: `AW-11396978687`; lead destination: `AW-11396978687/R0vKCKrFz9kcEP-vwLoq`.
- New routes inherit the root automatically. Do not add standalone public HTML or an independent `<html>/<body>` layout without review and reuse of the shared tag component. `proxy.ts` normalizes uppercase document paths by cloning the full URL, preserving arbitrary query parameters. API and file paths are excluded.

Run `npm run lint`, `npm run test:analytics`, `npx tsc --noEmit`, and `npm run build`. After building, run `node scripts/test-analytics-production.mjs` to check the minified bundle and bootstrap with Next scripts blocked. Browser tests use blocked Google requests and intercepted Make responses; they do not create real leads. The runner creates and removes a new landing route to test inheritance. CI checks direct tag calls, duplicate loaders, title conventions and layout bypasses. Never weaken these checks, change consent defaults, add automatic lead events, change conversion value/destination, or re-enable GA4 history tracking without review.

Release verification: use Tag Assistant plus GA4 DebugView on a real phone for home, service, blog and every landing page; check one clean page view with the full landing URL, then one successful lead pair and original click IDs in Airtable. Force a browser-intercepted webhook failure and verify zero conversions. Automated emulation is not a substitute for that sign-off. Release status and the exact selected files are in `ANALYTICS-RELEASE.md`.

## Exact Make response contract (unchanged)

Both `submitLead` and `submitLeadPayload` await `fetch`, then pass the browser Response to `confirmLeadResponse`. The only transport success condition is `response.ok`: any final HTTP status from 200 through 299. The client does not read or parse the response body and does not check an Airtable record ID, JSON success flag, Content-Type, or downstream completion. Thus 200 with `{ "success": false }`, 202 Accepted, and 204 No Content all count as successful submissions. Redirects use the Fetch default follow behavior; the final response status is evaluated.

A non-2xx final response throws. Network/CORS failures reject fetch. Both paths bypass the form success handler and emit no lead events. Validation failures do not call the transport. A successful Response is registered by the transport and may emit one Ads conversion and one GA4 generate_lead at most; passing the same response again does not emit another pair. The response object guard is not an Airtable acknowledgement.

To make Airtable completion the boundary without changing this client, Make must send a browser-readable 2xx only after the Airtable write succeeds, and a browser-readable non-2xx on failure. An early automatic 200/202 acknowledgment would count as success even if later steps fail. CORS must allow the site to read the response. Do not return an error flag inside HTTP 200 expecting this client to reject it. This documents the existing contract; it does not modify it.
